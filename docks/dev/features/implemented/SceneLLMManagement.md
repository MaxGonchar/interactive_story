# Feature: Scene LLM Management

**Status**: Draft  
**Date**: 2026-09-05

## Summary
This feature lets a user switch between available LLMs while playing a scene, without breaking the scene history or creating a separate model state machine. The backend owns the model registry, the default model is global, and the current model is inferred from the latest assistant response if the scene already has messages. When the scene is empty, the default model is used. Users can override that choice for the next turn by selecting another model from the UI.

## Value
- What problem it solves
  - Users cannot compare model behavior or continue a scene with a different model after the first turns.
  - The app currently relies on a single model configuration path and does not expose model choice in the play loop.
- How it fits the project's purpose
  - This is part of the core interactive scene experience: the player’s narrative flow depends on which model responds.
- Success criteria
  - The scene header shows the current model.
  - The user can choose a different model from a dropdown.
  - The next turn is generated by the selected model.
  - The assistant message stores which model produced it.

## Scope
- In scope for first iteration
  - Backend-owned registry of available models
  - Global default model configuration
  - Current model resolution from the latest assistant response or default model fallback
  - Optional model_id in the play request
  - llm_data.model_id saved on assistant messages
  - `GET /models` endpoint for UI consumption
  - Dropdown in the scene header for model selection
- Out of scope / future
  - Per-user default model preferences
  - Cost/token analytics UI
  - Per-scene locked model history or model timeline
  - Cross-scene model persistence outside the active flow

## User Flow
1. The user opens a scene.
2. The UI loads the scene and calls `GET /models`.
3. The backend resolves the current model as:
   - first turn: default model from the model registry
   - later turns: last assistant message’s llm_data.model_id
4. The scene header shows the current model and a list of available models.
5. The user selects a different model from the dropdown.
6. The next turn uses the selected model_id if supplied in the play request.
7. The backend runs the LLM with that model and stores the used model on the generated assistant message.
8. The next turn automatically reuses the last assistant model unless the user switches again.

## API Changes
### GET /api/models
Returns the backend-owned model registry and the default model.

Response:
```json
{
  "data": {
    "models": {
      "gpt-4o-mini": {
        "name": "GPT-4o-mini",
        "providerModelID": "gpt-4o-mini"
      },
      "llama-3.3-70b": {
        "name": "Llama 3.3 70B",
        "providerModelID": "llama-3.3-70b"
      }
    },
    "default_model_id": "gpt-4o-mini"
  }
}
```

### POST /api/stories/{story_id}/scenes/{scene_id}/play
Request is extended with optional model_id.

Request:
```json
{
  "content": "I look for the nearest light source.",
  "model_id": "llama-3.3-70b"
}
```

Behavior:
- If model_id is provided and valid, use it for this turn.
- If model_id is omitted, resolve the model from the latest assistant message or use the default model.
- Persist the model used on the generated assistant message.

Response:
```json
{
  "data": {
    "user_message": {
      "id": 2,
      "role": "user",
      "content": "I look for the nearest light source."
    },
    "assistant_message": {
      "id": 3,
      "role": "assistant",
      "content": "A lantern swings near a wooden post...",
      "llm_data": {
        "model_id": "llama-3.3-70b"
      }
    }
  }
}
```

## Data Changes
### Model registry
The canonical source of available models is stored in `data/models.yaml` on the backend.

Example:
```yaml
models:
  gpt-4o-mini:
    name: "GPT-4o-mini"
    providerModelID: "gpt-4o-mini"
    default: true
  llama-3.3-70b:
    name: "Llama 3.3 70B"
    providerModelID: "llama-3.3-70b"
    default: false
```

### Assistant message metadata
Each assistant message stores the model used to generate it.

```yaml
- id: 42
  role: "assistant"
  content: "You step into the quiet alley..."
  llm_data:
    model_id: "gpt-4o-mini"
```

This nested object is intentionally structured so future metadata such as tokens, cost, latency, or provider details can be added without changing the top-level file format.

### Model resolution rule
- If the scene has no messages, current model = default model from `data/models.yaml`
- If the scene has messages, current model = llm_data.model_id from the last assistant message
- If the user provides a model_id for the next request, use it for that generation and persist it on the assistant message
- No separate scene-level `active_model_id` field is stored for v1

## Backend Changes
- Add backend model registry loader for `data/models.yaml`
- Expose `GET /models` for UI model selection
- Extend the scene play service to accept optional model_id and resolve the actual model for that turn
- Update LLM client creation so the chosen model can be instantiated per request instead of only via a single global dependency
- Persist `llm_data.model_id` on every assistant message when the response is saved
- Validate that model_id exists in the registry before invoking the LLM
- Keep the default model global and centralized in the backend

## Frontend Changes
- Add a dropdown in the scene header next to the scene state indicator
- Fetch the list of available models from `GET /models` when the scene page loads
- Cache the model registry in frontend state for convenience, but treat the backend as the source of truth
- Resolve the current model from:
  - default model for empty scenes
  - last assistant message model for scenes with messages
- When the user selects another model, send it as `model_id` in the next play request
- Keep the dropdown in sync with the last successful assistant model unless the user changes it again

## Open Questions
- Should the UI refresh the model registry automatically after a period or only on scene load?
  - **Only on scene load**
- Do we want the default model to be a visible label in the UI or an implicit fallback only?
  - **No tags for now**

## Risks
- Model IDs may become stale if the model registry file is changed while the app is running.
- A selected model can be valid in the registry but unavailable from the provider at runtime; the backend should fail gracefully.
- The current model must be derived from the last assistant response, not from stale UI state, to avoid mismatches in the scene flow.
- Model selection must not break atomic write guarantees when appending messages to a scene.
